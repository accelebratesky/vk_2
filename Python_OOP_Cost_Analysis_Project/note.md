# 校园食堂消费分析 —— 我的思考与学习记录

> 这份 note 记录的不是“最后那份代码长什么样”，而是**我拿到题目以后，是怎么一点点把它想明白的**。
> 包括走过的那条弯路、卡住的地方、以及回头看才发现很简单的部分。

---

## 一、拿到题目，我先做的不是写代码

题目的原始要求其实很朴素：一个学生、7 天消费记录、要统计总消费、平均、最高最低、超平均天数、等级、连续高消费。

但我先问了自己一个问题：

***为什么这道题要用“类”，而不是继续像上一题那样，写一堆函数传 list 进去？***

如果按老办法写，大概是：

```python
def money(costs): ...
def cost_most(costs): ...
def cost_least(costs): ...
print(money(zhangsan_scores))
print(cost_most(zhangsan_scores))
```

能跑，但有问题：`costs` 这个参数要在**每一个函数里重复传**，如果以后要加一个“学生姓名”，每个函数都得跟着加一个参数。而且数据和函数是**散开的**，一转头就不知道 `zhangsan_scores` 是给哪套函数用的。

所以这道题真正想让我体会的是：***把“一个学生的数据”和“针对这些数据的操作”捆在一起***，让 `student.money()` 这种写法自己就知道该算谁的钱。

这一步想清楚之后，后面的设计就顺了：

- 属性：`name`、`costs`
- 方法：计算类（money / cost_most / cost_least / over_cost）、判定类（judge_cost / stage_all / connect_over_cost）、输出类（show_all）

---

## 二、第一版：先把“能算”写出来

我一开始是按“一个小功能 = 一个方法”来切的，顺序就是题目要求的顺序：

1. `money()` —— 总消费和平均，`sum` 除以 `len`
2. `cost_most()` —— 最高的一天
3. `cost_least()` —— 最低的一天

前两个很快就写完了，因为思路很直：**先算出数值（sum / max / min），再去找这个数值在第几天。**

### 卡住的地方：怎么知道是“第几天”？

这里我第一反应不是用 `self.costs.index(x)`，而是想自己遍历一遍。原因是前一题刚练过手写查找，我想再走一遍流程：

```python
biggest_cost = max(self.costs)
count = 1
for cost in self.costs:
    if cost == biggest_cost:
        break
    count += 1
```

`count` 从 1 开始，是因为**题目说“第1天”，不是“第0天”**。遍历到目标值就 `break`，`count` 就是天数。

> 后来反应过来：`self.costs.index(x) + 1` 一行就完事了。但手写这一遍也不亏 —— 我确认了自己能说清楚“为什么 count 从 1 开始”。

## 三、真正让我卡住的地方：连续两天超过 60 元

这个是最绕的。我当时的脑回路是：**“连续两天”就是“要记住前一天的状态”**，所以我直接写了一个状态机：

```python
state = 0     # 0 = 今天没超过 60，1 = 今天超过了 60
count = 0
for cost in self.costs:
    if state == 0:
        count += 1
        if cost > 60:
            state = 1
    elif state == 1:
        if cost > 60:
            print(...)
        else:
            state = 0
```

跑到最后确实能出结果，但写的时候一直在数 `count`，还要想 `count+1` 到底是对应今天还是明天，**非常容易 off-by-one**。

而且它有个隐藏毛病：如果出现“连续三天都超过 60”，程序会输出“第1天和第2天”“第2天和第3天”两次 —— 严格说是对的（三连也确实包含两组相邻），但读起来像重复了。

**后来突然反应过来**，其实根本不用什么状态机：

```python
for count in range(len(self.costs) - 1):
    if self.costs[count] > 60 and self.costs[count + 1] > 60:
        print(f"发现连续高消费：第{count+1}天和第{count+2}天")
```

“连续两天”这个条件，本来就只需要**同时看相邻的两个下标**。`range(len(costs) - 1)` 保证 `count + 1` 不越界，判断里直接写两个条件同时成立，就这么简单。

我在笔记里当时的原话是：

> “我真傻，后面才反应过来直接这样写不就行了吗，可能上一题写了状态机这一题还想着吧……”

***这就是这道题给我最大的教训：状态机是给“需要记住历史”的问题准备的，而“相邻两天”这种局部判断，根本不需要记住任何东西。*** 被我上一题的惯性带跑了。

## 四、反复改输出格式：从“能跑”到“像作业”

我的第一版能出结果，但输出是这样的：

```
平均每天消费：48.4375元
biggest_cost: 88 天数： 8
over_cost天数： 7
```

问题很明显：

1. **小数太长** —— 题目示例是 `49.43元`，两位小数。这是 `f"{x:.2f}"` 该干的事。
2. **`biggest_cost:` 是调试口吻** —— 交作业不应该出现英文变量名直接打印。
3. **顺序和题目不一致** —— 题目是先总消费、再平均，我一开始写反了。
4. **更严重的问题：我把张三的数据写成了 16 天。** 题目反复强调“连续 7 天”“7 天食堂消费记录”，我却在示例数据后面又手动加了 9 个数做“测试”。结果算出来的总消费是 775 元、平均 48.43 元，和题目给的 `346 元`、`49.43 元` 对不上。

第 4 点是**最容易扣分却最不容易自己发现**的 —— 因为程序不报错，它只是默默地算错了。我的做法是：**拿题目给的示例输出当“正确答案”，逐行对照。**

```
题目：本周总消费：346元      我的：775元     ← 数据错了
题目：平均每天消费：49.43元   我的：48.4375元  ← 格式 + 数据都错了
题目：消费最高：第6天，63元   我的：88 天数：8  ← 数据多了
```

对照完我就把数据改回题目给的 `[42, 35, 48, 58, 61, 63, 39]`，一行一行对，直到 8 行输出**逐字一致**。这个过程本身很有价值：***“拿预期输出当测试用例”比自己随便造数据靠谱得多。***

## 五、最后的整理：把重复的东西收起来

改格式的时候发现两个可以优化的地方：

### 1. 等级判断不该埋在打印里

我原来是在 `stage_all()` 里直接 `if cost < 40: print("节省")`。问题是：**如果以后我要判断“某一天是不是偏高”，难道还要再写一遍 if？**

所以把判断单独抽成一个方法：

```python
def judge_cost(self, cost):
    if cost < self.LOW_LINE:
        return "节省"
    elif cost <= self.HIGH_LINE:
        return "正常"
    else:
        return "偏高"
```

`stage_all()` 就变成“遍历 + 调用 + 打印”，职责单一。***这是一个方法只做一件事的思路：judge 负责判断，print 负责输出。***

### 2. 阈值 40 / 60 是“魔法数字”

代码里到处出现 `40`、`60`，如果老师把标准改成 45 / 70，我得全文搜索。所以放到类属性：

```python
class StudentCost:
    LOW_LINE = 40
    HIGH_LINE = 60
```

用的时候写 `self.LOW_LINE`。这样只改一处，全部生效。

### 3. over_cost 不要重算平均值

原来 `over_cost()` 里又把 `sum / len` 写了一遍，等于和 `money()` 重复。改成直接复用：

```python
pinjun_money, all_money = self.money()
```

***同一个类里的方法可以互相调用（`self.方法名()`），这是“封装”的好处之一。***

## 六、边界测试：40 和 60 到底算哪一档？

题目写的是：

| 金额 | 等级 |
|---|---|
| 小于 40 | 节省 |
| 40～60 | 正常 |
| 大于 60 | 偏高 |

所以 **40 是“正常”，60 也是“正常”，61 才“偏高”**。

我专门造了一个学生来验证这个边界：

```python
student3 = StudentCost("王五", [38.5, 40, 60, 61, 39.5, 20, 12])
```

跑出来：

```
第1天：38.5元，节省     ← 38.5 < 40
第2天：40元，正常       ← 边界值落在正常
第3天：60元，正常       ← 边界值落在正常
第4天：61元，偏高       ← 只多 1 元就跨档
```

如果这里写成 `elif cost < 60`，60 就会被误判成“偏高”，而程序不会报错。***边界值是最容易写错、又最不容易发现的地方，所以要主动造数据去测。***

这个用例还顺带测了另一件事：`connect_over_cost()` 在**找不到**连续高消费时会怎样。原来的版本是什么都不打印，屏幕上就空一行，看不出是“没有”还是“程序崩了”。所以我加了一个 `found` 标记，没有就明确打印“未发现连续两天消费超过60元”。

## 七、我对“类、对象、属性、方法”的理解

- ***类（class）是一张模板 / 设计图***。`StudentCost` 定义的是“一个学生消费分析对象应该有哪些数据、能做哪些事”，它本身不装任何具体分数。写好类的那一刻，程序里其实还没有任何真实数据。
- ***对象（object / 实例）是按模板造出来的具体个体***。`student = StudentCost("张三", [...])` 这一行才真正造出一个对象，`student2` 又是另一个独立对象。
- ***属性（attribute）是对象自己身上背着的数据***。`self.name`、`self.costs` 属于张三；李四有他自己的 `self.costs`，两个列表互不影响。
- ***方法（method）是绑在对象身上的函数***。它比普通函数多一个 `self`，因为方法需要一个“我”来知道**对谁的数据做运算**。

### 为什么同一个类能分析不同学生？

因为 ***类里存的是“逻辑”，对象里存的是“数据”***。

`show_all()` 这段代码只写了一份，但里面每次用到 `self.costs`、`self.name`，`self` 指向谁，用的就是谁的数据：

- `student.show_all()` → `self` 是 student → 算张三的 346 元
- `student2.show_all()` → `self` 是 student2 → 算李四的 315 元

所以不是“代码复制了两遍”，而是***同一套计算流程，被两个不同的 `self` 各用了一次***。这也是面向对象最实际的好处：**新增一个学生，只需要 `StudentCost("王五", [...])` 一行，不用写任何新函数。**

## 八、如果还有时间，我会继续做

1. `costs` 长度不做检查 —— 现在 `money()` 里直接 `len(self.costs)`，如果传入空列表会 `ZeroDivisionError`；如果传入 14 天也不会报错（我最早就是这么“偷偷”跑了 16 天）。可以在 `__init__` 里加一句长度校验。
2. `show_all()` 现在直接用 `print` 输出，如果以后想存成文件或者网页，就得改方法内部。更彻底的做法是让方法 **返回数据**（比如返回一个 dict / 列表），由外面决定怎么显示 —— 这叫“输出与业务分离”，是后面学 Web / 数据分析时的习惯。
3. `judge_cost()` 里的 if-elif-else 是用“区间”表达的，如果以后等级变成 5 档、10 档，写起来会很长，那时才需要考虑用字典 + 阈值表。

---

## 九、一句话总结这次学到的东西

> ***类的意义不是“把函数塞进一个 class 里”，而是让数据和操作它的逻辑待在一块，让 `self` 去区分“这一次算的是谁”。***
> ***而写代码时最该警惕的，往往不是语法报错，而是“程序跑通了，但结果是错的” —— 所以一定要拿预期结果去对照。***
